**读者**：系统使用方、测评/检测人员。本文说明**系统是怎么设计的、有哪些功能**。

## 1. 设计目标与总体形态

> 术语约定：《测试需求.md》§1.2 表述为“单机构部署形态”，本文按实现侧叫法称单租户；使用方机构在界面与代码中写作“组织 / org”。

| 设计目标 | 落地方式 |
|---|---|
| 一个能真实跑起来的检测机构业务系统 | 覆盖账户权限、检测项目、审计日志、数据备份恢复、帮助与初始化的完整闭环 |
| 轻量化，各组织可统一搭建 | 浏览器直接使用，服务端不需安装额外组件；数据由两个建库脚本一次生成 |
| 分级权限、操作可留痕 | 4 个角色 + 15 项权限；关键操作统一写审计日志 |
| 缺陷常态化、可被检出 | 功能"看着完整、按标准核查即不合规"，与合规实现共用同一套界面与流程 |

系统支持两种部署形态，同一套代码自适应，按是否导入平台库决定：

- 单租户：一套业务数据，组织内部直接使用，也是接受测评时的默认形态
- **多租户**（扩展能力）：平台端统一管理多个检测机构，每个组织拥有独立的一套业务数据与独立入口

## 2. 功能设计（有哪些功能）

### 2.1 功能地图

下表给出六个功能模块与《测试需求》§3.1 各小节的对应关系；平台端不在需求范围内，属实现侧扩展（§2.9）。

| 模块 | 需求条款 | 入口 | 可执行的操作 | 侧栏对哪些角色可见 |
|---|---|---|---|---|
| 登录与退出 | §3.1.1 | `/login` | 帐户名口令登录、退出登录 | 公开页 |
| 首页（仪表板） | §3.1.2 | `/dashboard` | 统计卡片、最近 5 条项目、最近 10 条操作日志、角色快捷入口与帮助入口 | 全部角色 |
| 用户管理 | §3.1.3 | `/user/list` | 分页浏览用户、新建用户、编辑用户、删除用户 | 超级管理员、普通管理员 |
| 项目管理 | §3.1.4 | `/project/list` | 分页浏览项目、新建项目、编辑项目、删除项目 | 超级管理员、操作员 |
| 审计日志 | §3.1.5 | `/audit/list` | 分页浏览审计记录、删除单条、批量删除、清空全部、导出 CSV、审计与审计备份开关 | 超级管理员、审计管理员 |
| 备份与恢复 | §3.1.6 | `/backup/list` | 查看备份与恢复记录、执行手动备份、恢复、下载、自动备份开关 | 超级管理员、普通管理员 |
| 帮助中心 | §3.1.7 | `/help/faq` | 常见问题 / 用户手册 / 安全指南 / 系统设置；仅超级管理员可初始化系统 | 全部角色 |
| 平台端（扩展） |：| `/platform/...` | 平台登录与首跑设口令；组织的登记、查看、修改、启停、重置、下线；平台操作留痕 | 平台管理员 |

列表类页面统一按每页 10 条翻页。

### 2.2 登录与退出

1. 在登录页输入帐户名与口令；帐户名或口令错误不能进入系统。
2. 登录成功后进入首页（仪表板），系统建立登录会话并记录最近登录时间与登录 IP。
3. 登录状态下，系统在 Cookie 中保存当前登录用户信息用于维持会话。
4. 在主界面选择【登出】并确认后退出系统，返回登录页。
5. 会话信息保存在服务端；会话目录不可写会导致登录后又被弹回登录页。
6. 多租户形态（扩展能力，见 §6）下，平台管理员与各组织用户分属两套账户，互不能代替对方登录。

### 2.3 首页（仪表板）

- 卡片式运行统计：活跃用户数、检测项目数、审计日志数、备份记录数；
- 最近 5 条检测项目列表，点击项目名称可直达该项目的编辑页；
- 最近 10 条操作日志列表（时间、用户、操作类型）；
- 按当前角色显示功能快捷入口（项目管理 / 用户管理 / 审计日志 / 备份管理）；
- 帮助文档入口（常见问题 / 用户手册 / 安全指南 / 系统设置）；
- 额外显示当前登录者的账号与角色、本机 PHP 与 MySQL 运行环境信息（便于搭建排障）。

任一统计取不到数时以 0 展示，不影响页面打开。

### 2.4 用户管理

- 用户列表：用户 ID、角色、用户名、姓名、电话、状态、创建时间，每页 10 条；已删除账户不出现；非超级管理员看不到针对超级管理员的操作按钮。
- 新建用户：填写用户名、密码、姓名、工号、电话与角色后提交，保存后自动刷新列表。用户名、密码、姓名、电话为必填；密码长度不低于 6 位，且 6 位密码不能为纯数字；角色可选普通管理员、操作员、审计管理员，或选择“不选择（空权限）”；不允许通过本页面创建超级管理员。
- 编辑用户：可修改用户名、密码（留空则不修改）、姓名、电话、状态（激活 / 禁用 / 锁定）与角色，保存后自动刷新列表。
- 删除用户：二次确认后执行，删除后自动刷新列表；不允许删除自己，不能删除内置 `admin` 账户，非超级管理员不能删除超级管理员；删除会连带清除该账户的角色关联。

### 2.5 项目管理

- 项目列表：项目 ID、项目名称、项目代码、状态、创建人、创建时间，每页 10 条。
- 新建项目：填写项目名称、项目代码、描述并提交，项目初始状态为“草稿”（负责人与创建人由系统记录），保存后自动刷新列表。
- 编辑项目：可修改项目名称、项目代码、状态（草稿 / 已提交 / 已审核 / 已存档）与描述，保存后自动刷新列表。
- 删除项目：二次确认后执行，删除后自动刷新列表。

> 数据层面另有一张检测结果明细表（项目下的逐条检测项与结论），当前版本未提供录入与展示界面，属预留结构。

### 2.6 审计日志

- 浏览：以列表形式显示所有帐户的操作日志，包括时间、用户、操作类型、对象类型、操作描述、客户端 IP、结果，每页 10 条；操作类型与结果以彩色徽章区分。
- 操作类型覆盖：登录、登出、创建/更新/删除用户、创建/更新/删除项目、删除审计日志、备份、恢复等。
- 删除：可删除单条、勾选批量删除、一键清空全部。勾选列与删除操作对超级管理员、审计管理员开放，与需求 §3.1.5 一致。
- 导出：导出 CSV 格式的日志数据文件，列为时间、用户、操作类型、对象类型、操作描述、客户端 IP、结果。
- 开关：提供“审计日志”与“审计日志备份”两个启用/关闭开关，开关状态影响后续是否留痕。
- 容量：写入前比对配置的容量上限，达到上限后不再新增记录；需求 §3.1.5 规定的容量为 30000 条，实际取值与超限行为属检测点（编号见《缺陷清单.md》）。

### 2.7 备份与恢复

- 记录列表：备份记录含备份 ID、备份时间、大小、类型、状态，每行提供“恢复”与“下载”操作；恢复记录含恢复 ID、恢复时间、备份 ID、操作者、状态、说明。
- 执行手动备份：将当前业务数据库导出为 SQL 备份文件（保存在服务器端备份目录，命名形如 `backup_20260927162731.sql`），并生成一条备份记录。
- 恢复：点击备份记录的“恢复”并确认后，系统用该备份文件恢复数据库，并生成恢复记录。
- 下载：可下载任意一份备份文件。
- 自动备份：提供启用/关闭开关，开启后按固定周期执行自动备份。
- 权限：仅超级管理员与普通管理员具备备份管理操作权限。

### 2.8 帮助中心

- 常见问题：以问答形式提供系统使用说明（登录、权限、项目、备份、审计等）。
- 用户手册：提供登录与访问、项目管理、用户管理、审计日志、备份管理、退出登录等操作说明。
- 安全指南：提供账号与密码、访问控制、会话安全、审计与日志、数据备份等安全建议。
- 系统设置：提供基本配置、备份策略、安全策略、系统维护说明（当前为说明性内容，不做配置项的读取与保存）。
- 初始化系统：仅超级管理员可见与可执行，清空全部数据并按照初始脚本重建系统数据，供演示与重复练习使用，操作不可撤销。

### 2.9 平台端与组织生命周期（扩展能力）

平台端与多租户能力超出《测试需求.md》§1.2 规定的单租户形态，属实现侧扩展：未导入平台库时不启用，不影响任何测评基准。平台端面向运营方，功能按组织生命周期排列：

| 环节 | 界面操作 | 结果 |
|---|---|---|
| 平台登录 | 首次访问设置平台管理员口令，此后凭口令登录 | 进入平台控制台 |
| 登记组织 | 填写组织代号、名称、说明 | 生成一条组织记录，并为其准备独立的业务数据与一个组织管理员账号 |
| 交付信息查看 | 组织详情页 | 显示组织入口地址、管理员账号与初始口令、数据库连接信息 |
| 启停 | 启用 / 停用 | 停用后该组织入口不再可用，组织记录保留 |
| 重置 | 初始化组织数据 | 把该组织那套业务数据重建为初始状态（口令等凭据不变） |
| 修改 | 编辑名称、说明、状态 | 更新组织记录 |
| 下线 | 删除组织 | 删除组织记录，并连带清理其独立业务数据与账号 |
| 留痕 | 平台操作日志 | 平台侧的登录与组织变更操作单独成表保存 |

每个组织都有独立入口 `/{org_code}/login`（组织代号），组织内的用户、项目、审计、备份数据彼此隔离。

## 3. 角色与权限设计

### 3.1 角色

角色划分与模块访问范围以《测试需求.md》§3.2（表 2 模块访问权限表）为准；实现中的定位：

| 角色 | 定位 |
|---|---|
| 超级管理员 `super_admin` | 系统最高权限，含审计删除、系统设置与初始化、组织管理 |
| 普通管理员 `admin` | 日常运营：用户管理与备份 |
| 操作员 `operator` | 业务数据操作：检测项目的增删改 |
| 审计管理员 `auditor` | 只面向审计日志的查看与核查 |

### 3.2 权限项（15 项）

按模块划分：用户 `view/create/edit/delete`、角色 `role.manage`、权限 `permission.manage`、项目 `view/create/edit/delete`、审计 `audit.view`、审计删除 `audit.delete`、系统设置 `system.settings`、备份 `backup.manage`、报告导出 `report.export`。

初始授权范围：

| 角色 | 被授予的权限 | 数量 |
|---|---|---:|
| 超级管理员 | 全部 | 15 |
| 普通管理员 | 除角色管理、权限管理、系统设置、审计删除之外 | 11 |
| 操作员 | 项目相关四项 | 4 |
| 审计管理员 | 审计查看 | 1 |

### 3.3 权限的实际生效方式

系统里的“权限”有两层，评估时需要区分：

1. **菜单可见性**：按角色裁剪，决定用户"看得到哪些入口"。
2. **服务端访问判定**：页面与操作是否放行。当前设计的判定粒度为“是否已登录 + 角色字符串”，并不逐项比对 §3.2 的授权数据**，也未完全按需求表 2 的模块访问范围拦截，例如系统设置页面对已登录用户普遍可见；平台管理员会话按平台侧放行。

因此某角色被授予的权限与实际可访问的功能是两套口径，评估以实际访问结果为准，对应编号见《缺陷清单.md》。

## 4. 数据设计

### 4.1 数据对象一览

业务侧（每套业务数据 13 张表）

| 数据对象 | 存什么 |
|---|---|
| 用户账户 | 账号、口令、姓名、工号、手机号、邮箱、状态、角色归属、最近登录、登录失败计数、是否需改密 |
| 角色 / 权限 / 角色权限 / 用户角色 | 分级权限体系的四张关联对象 |
| 检测项目 | 项目编号、名称、负责人、说明、状态、创建与更新信息、数据校验位 |
| 检测结果明细 | 项目下的逐条检测项、结果值与结论（预留结构，当前无界面） |
| 审计日志 | 操作时间、账号与角色、操作类型、对象、描述、变更前后值、客户端 IP、结果 |
| 登录流水 | 登录结果、IP、浏览器信息（结构存在，当前无写入） |
| 备份记录 / 恢复记录 | 每次备份与恢复的元信息与结果 |
| 系统参数 | 审计开关、审计容量上限、会话超时、密码有效期、备份计划、登录失败锁定阈值等 |
| 审计参数 | 审计启用、数据库操作留痕、登录留痕、保留时长、清理周期 |

**平台侧（3 张）**：组织登记（代号、名称、独立数据位置与连接账号、状态、联系人与备注）、平台管理员、平台操作留痕。

### 4.2 对象关系

```text
平台侧                                  业务侧（单租户一套 / 每组织各一套）
组织登记 ─── 一个组织对应一套独立业务数据 ───┐
平台管理员                                  │
平台操作留痕                                ▼
                                    用户账户 ──┬── 用户角色 ── 角色 ── 角色权限 ── 权限
                                               │
                                               ├── 检测项目 ── 检测结果明细
                                               │
                                               ├── 审计日志
                                               ├── 登录流水
                                               └── 备份记录 ── 恢复记录
                                    系统参数 / 审计参数（全局配置）
```

组织与业务数据之间**不做跨库关联**，只靠"组织代号 ↔ 数据位置"的对应关系联系。

### 4.3 主要状态取值

| 对象 | 取值 | 界面呈现 |
|---|---|---|
| 用户账户状态 | `active` / `inactive` / `locked` / `deleted` | 启用 / 禁用 / 锁定 / 已删除 |
| 检测项目状态 | `draft` / `submitted` / `reviewed` / `archived` | 草稿 / 已提交 / 已审核 / 已存档 |
| 备份、恢复结果 | `success` / `failed` / `partial`；`completed` / `failed` | 成功 / 失败 / 部分成功；已完成 / 失败 |
| 组织状态 | `active` / `inactive` / `deleted` | 正常 / 已停用 / 已删除 |
| 审计结果 | `success` / `failed` / `partial` | 成功 / 失败 / 部分 |

### 4.4 参数项的实际使用

系统参数表中的配置项只有一部分被代码读取：审计容量上限与审计开关；会话超时、密码有效期、备份计划、登录失败锁定与锁定时长、以及审计参数表中的多数项目前只作为数据存在，不改变系统行为。这也是测评时的观察点（编号见《缺陷清单.md》）。

### 4.5 初始数据

一套业务数据初始化后即包含：4 个角色、15 项权限、按 §3.2 的授权关联、1 个内置超级管理员账户（含默认口令）、若干系统参数与审计参数；平台侧初始化后包含 1 个平台管理员账户与空的组织表。所有人名、项目名、日志内容均为虚构演示数据。

## 5. 界面与信息架构

- 整体布局：左侧固定导航栏（按角色裁剪、当前项高亮、底部显示当前用户与退出入口）+ 顶部面包屑与页标题 + 内容区；登录与首跑设置页使用独立的居中版式。平台端使用另一套同结构的外壳，与组织后台在视觉上区分。
- 页面构成：每页依次为页头（标题、说明、右上操作按钮）、提示条（成功、警告或失败）、数据面板（表格或表单）、分页条。
- 组件口径：表格、按钮、输入框与下拉、统计卡、徽章、提示条、分页等样式集中在一处维护，各页面复用同一套，因此同类元素在全站外观一致；状态、角色、操作类型一律用徽章呈现，颜色语义固定（正常绿、警告黄、错误红、信息蓝、中性灰）。
- 图标：内建一套 SVG 图标集，界面图标全部取自其中，不使用 emoji。
- 交互：删除、清空、恢复等破坏性操作均有二次确认；备份文件下载与审计导出直接由浏览器接管；表单提交后回跳列表并给出结果提示。
- 适配：以桌面浏览器为主要目标，宽度不足时表格与导航降级为可横向滚动的紧凑排布。

## 6. 访问形态与入口

| 形态 | 入口 | 使用者 | 数据 |
|---|---|---|---|
| 单租户 | `/login` | 组织内部各角色 | 默认的一套业务数据 |
| 平台端（扩展） | `/platform/login` | 运营方平台管理员 | 组织登记与平台留痕 |
| 组织端（扩展） | `/{org_code}/login` | 该组织各角色 | 该组织独立的一套业务数据 |

- 三者共用同一套代码，按访问地址自动判定；平台库不存在或未导入时，系统按单租户形态运行，不会报错。
- 项目必须放在 ASCII 目录名下（或用虚拟主机把站点根直接指向本项目），否则地址解析会错乱。原因见 `AGENTS.md`。
- 平台管理员口令在首次访问平台端时自行设置，系统不提供找回入口（只能改库，见《部署与运行指南.md》）。
