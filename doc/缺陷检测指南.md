## 二、检测方法概览

### 1. 数据库查询法

适用：DEF001/002/005/011/014/019/027/029/030 等

```sql
-- 查看用户表结构与数据（明文密码、必填手机号、无唯一约束）
DESCRIBE users;
SELECT id, username, password_hash, phone FROM users LIMIT 5;

-- 查看默认账户
SELECT * FROM users WHERE username IN ('admin','superadmin');

-- 审计日志结构与字段
DESCRIBE audit_logs;
SELECT operation_time, username, client_ip FROM audit_logs ORDER BY id DESC LIMIT 3;
```

### 2. API 抓包法

适用：DEF006/007/008/010

- 用 Burp Suite / Fiddler 代理拦截登录请求，观察账密是否明文、协议是否为 HTTP
- 检查响应头 `Set-Cookie` 是否包含 `username`、`user_id`、`auth_key`
- 拦截业务数据提交请求，篡改参数后放行，观察系统是否接受篡改数据

### 3. 权限测试法

适用：DEF003/004/020/023

- 用普通角色账户访问管理功能（用户管理、审计删除等），观察是否被拦截
- 创建用户时不选择角色，观察是否成功、能否登录
- 尝试用非超级管理员账户关闭审计开关

### 4. 代码审计法

适用：全部缺陷

- 按下列清单中的“代码位置”逐项核对
- 重点关注 `index.php` 的辅助函数（`hasPermission`、`auditLog`）与各控制器中的 `DEF0xx` 注释

## 三、缺陷详细清单

### 保密性（DEF001–DEF009）

---

#### DEF001：默认账户未删除/重命名

- **标准要求**：《测试需求.md》§3.3.1.2（应重命名或删除默认帐户，修改默认口令）；分类依据 GB/T 25000.51-2016 保密性
- **缺陷描述**：系统保留固定内置默认账户，种子数据写入 `superadmin`，未重命名、未删除，且可直接凭默认口令登录（《测试需求.md》§3.3.1.2 要求重命名或删除默认帐户、修改默认帐户的默认口令并及时停用多余过期账户；需求 §3.1.3.1 另提到内置 admin 用户，本样品业务库的内置账户为 `superadmin`，同属未删除、未重命名的通用默认账户）
- **代码位置**：
  - `sql/业务库建库脚本.sql` → `INSERT INTO users ... VALUES ('superadmin', ...)`
  - `LoginController.php` → `authenticate()`（注释 DEF001：内置默认账户可直接登录）
- **检测方法**：
  1. 用 `superadmin` + `123456` 尝试登录
  2. 查询 `SELECT * FROM users`，确认内置账户存在且未要求改名
- **预期结果**：✓ 缺陷存在

#### DEF002：默认密码未强制修改、首次登录无强制改密

- **标准要求**：《测试需求.md》§3.3.5.2（首次登录应更改密码）、§3.3.1.2；分类依据 GB/T 25000.51-2016 保密性
- **缺陷描述**：默认密码 `123456` 永久有效；`users.must_change_password` 字段存在但登录流程不检查，首次登录直接进入系统
- **代码位置**：
  - `sql/业务库建库脚本.sql` → `must_change_password` 列（注释：DEF002 首次登录无强制改密）
  - `LoginController.php` → `authenticate()`（注释 DEF002：首次登录无强制改密）
- **检测方法**：新建用户后用初始密码登录，观察是否强制要求修改密码
- **预期结果**：✓ 缺陷存在（可直接登录）

#### DEF003：权限检查弱化，可越权访问管理功能

- **标准要求**：《测试需求.md》§3.3.1.1（权限相互隔离，禁止越权操作）、§3.3.1.4、§3.3.1.3；分类依据 GB/T 25000.51-2016 保密性
- **缺陷描述**：`hasPermission()` 仅判断角色是否在合法角色列表中，不做功能级权限校验，任意已登录用户均可访问管理功能
- **代码位置**：`index.php` → `hasPermission()`（注释：DEF003 权限检查弱化）
- **检测方法**：用 `operator`/`auditor` 账户直接访问 `/user/list`、`/audit/deleteall` 等管理路径
- **预期结果**：✓ 缺陷存在（越权成功）

#### DEF004：空权限账户可创建且可登录

- **标准要求**：《测试需求.md》§3.3.1.1（应对登录的用户分配帐户和权限）、§3.3.1.4；分类依据 GB/T 25000.51-2016 保密性
- **缺陷描述**：创建用户时不强制选择角色，未分配任何角色的空权限账户可正常创建并登录系统
- **代码位置**：`UserController.php` → `save()`（注释：DEF004 允许空权限账户创建）
- **检测方法**：创建用户时不选角色 → 用该账户登录
- **预期结果**：✓ 缺陷存在

#### DEF005：密码明文存储

- **标准要求**：《测试需求.md》§3.3.1.5（鉴别数据存储采用密码技术保护）；分类依据 GB/T 25000.51-2016 保密性
- **缺陷描述**：密码不做任何加密直接存入 `users.password_hash`，登录时明文比对
- **代码位置**：
  - `UserController.php` → `save()`（`$password_hash = $password;`，注释 DEF005）
  - `LoginController.php` → `authenticate()`（`$user['password_hash'] !== $password`，注释 DEF005）
  - `sql/业务库建库脚本.sql` → `password_hash` 列（注释 DEF005）
- **检测方法**：`SELECT password_hash FROM users LIMIT 1;` 可见明文
- **预期结果**：✓ 缺陷存在

#### DEF006：登录凭证 HTTP 明文传输

- **标准要求**：《测试需求.md》§3.3.1.5（鉴别数据传输采用密码技术保护）；分类依据 GB/T 25000.51-2016 保密性
- **缺陷描述**：登录请求无加密处理（HTTP 明文），抓包可直接获取完整鉴别数据；系统无 HTTPS 强制
- **代码位置**：`LoginController.php` → `authenticate()`（注释 DEF006）
- **检测方法**：Burp Suite 拦截登录请求，查看 `username=...&password=...` 明文
- **预期结果**：✓ 缺陷存在

#### DEF007：Cookie 明文存储用户账号

- **标准要求**：《测试需求.md》§3.3.1.6（禁止在 Cookie 中保存用户鉴别数据）；分类依据 GB/T 25000.51-2016 保密性
- **缺陷描述**：登录成功后向 Cookie 写入明文用户名 `username`
- **代码位置**：`LoginController.php` → `authenticate()`（`setcookie('username', $user['username'], ...)`，注释 DEF007, DEF008）
- **检测方法**：登录后查看浏览器 Cookie 或抓包响应头 `Set-Cookie`
- **预期结果**：✓ 缺陷存在

#### DEF008：Cookie 留存登录密钥，可篡改复用

- **标准要求**：《测试需求.md》§3.3.1.6（禁止在 Cookie 中保存用户鉴别数据）；分类依据 GB/T 25000.51-2016 保密性
- **缺陷描述**：Cookie 中写入 `user_id` 与 `auth_key`（`md5(id+username)`，可离线推算），篡改 Cookie 可实现无密码登录
- **代码位置**：`LoginController.php` → `authenticate()`（`setcookie('user_id', ...)`、`setcookie('auth_key', md5($user['id'] . $user['username']), ...)`）
- **检测方法**：复制登录后的 Cookie 到另一浏览器/无痕窗口直接访问受保护页面
- **预期结果**：✓ 缺陷存在

#### DEF009：密码无复杂度校验

- **标准要求**：《测试需求.md》§3.1.3.2（密码长度不低于 6 位，6 位不能为纯数字）、§3.3.5.1；分类依据 GB/T 25000.51-2016 保密性
- **缺陷描述**：仅校验长度 ≥6 位且 6 位纯数字被拒，无大小写/特殊符号/8 位复杂度要求
- **代码位置**：`UserController.php` → `save()`（注释 DEF009 不检查密码复杂度）
- **检测方法**：创建密码为 `abcdefg`（7 位纯小写）或 `1234567` 的用户，观察是否被接受
- **预期结果**：✓ 缺陷存在

### 完整性（DEF010–DEF013）

---

#### DEF010：业务数据传输无完整性校验

- **标准要求**：《测试需求.md》§3.3.2.1（重要数据传输需校验技术保证完整性）；分类依据 GB/T 25000.51-2016 完整性
- **缺陷描述**：检测项目等核心业务数据传输无 MD5/SHA 校验值，抓包篡改后系统正常接收并保存
- **代码位置**：`ProjectController.php` → `save()`/`update()`；`sql/业务库建库脚本.sql`（注释 DEF010）
- **检测方法**：拦截数据提交请求，篡改 `project_name` 等字段后放行，刷新页面确认篡改生效
- **预期结果**：✓ 缺陷存在

#### DEF011：数据库存储无有效校验字段

- **标准要求**：《测试需求.md》§3.3.2.1（重要数据存储需校验技术保证完整性）；分类依据 GB/T 25000.51-2016 完整性
- **缺陷描述**：`detection_projects.data_integrity_check` 字段存在但从不计算/校验，直接改库后系统无任何识别、告警
- **代码位置**：`sql/业务库建库脚本.sql` → `data_integrity_check` 列（注释 DEF011）
- **检测方法**：直接 `UPDATE detection_projects SET project_name='HACKED' WHERE id=1;` 后刷新页面
- **预期结果**：✓ 缺陷存在（无告警）

#### DEF012：自动备份功能失效

- **标准要求**：《测试需求.md》§3.3.2.2（提供业务数据备份与恢复）、§3.1.6（自动备份按固定周期执行）；分类依据 GB/T 25000.51-2016 完整性
- **缺陷描述**：自动备份仅是一个会话级开关（`$_SESSION['auto_backup_enabled']`），无定时任务、无执行日志、无自动备份文件生成
- **代码位置**：`BackupController.php` → `toggleauto()`；`sql/业务库建库脚本.sql`（注释 DEF012-013）
- **检测方法**：开启自动备份后等待/重启，检查 `backup_records` 表与 `backups/` 目录，确认无自动备份记录
- **预期结果**：✓ 缺陷存在

#### DEF013：备份恢复数据不完整

- **标准要求**：《测试需求.md》§3.3.2.2（恢复后数据无丢失）、§3.1.6；分类依据 GB/T 25000.51-2016 完整性
- **缺陷描述**：备份恢复后最新新增的部分业务数据丢失，恢复不完整
- **代码位置**：`BackupController.php` → `restore()`；`sql/业务库建库脚本.sql`（注释 DEF012-013）
- **检测方法**：记录项目数 → 新增若干项目 → 备份 → 再新增项目 → 恢复到先前备份，对比恢复前后数据量
- **预期结果**：✓ 缺陷存在

### 抗抵赖性（DEF014–DEF015）

---

#### DEF014：删除操作无抗抵赖签章

- **标准要求**：《测试需求.md》§3.3.3（关键操作不可抵赖、可追溯）；分类依据 GB/T 25000.51-2016 抗抵赖性
- **缺陷描述**：`detection_results.signature_hash` 字段存在但从不写入/校验，删除等关键操作无唯一校验标识、无有效凭证追溯
- **代码位置**：`sql/业务库建库脚本.sql` → `signature_hash` 列（注释 DEF014）
- **检测方法**：执行删除操作后查询审计记录，确认无签章/签名信息
- **预期结果**：✓ 缺陷存在

#### DEF015：操作时间戳无固化机制

- **标准要求**：《测试需求.md》§3.3.3（操作时间戳可证实、不可篡改）；分类依据 GB/T 25000.51-2016 抗抵赖性
- **缺陷描述**：审计/操作时间由 `date()` 取应用服务器时间（PHP 系统时间），无时间戳固化（应使用数据库时间戳），修改系统时间即可篡改操作记录实现抵赖
- **代码位置**：`index.php` → `auditLog()`（`date('Y-m-d')` 写入时间，注释 DEF015）
- **检测方法**：修改系统时间后执行操作，观察审计日志时间随系统时间变化
- **预期结果**：✓ 缺陷存在

### 可核查性（DEF016–DEF026）

---

#### DEF016：删除操作可能不纳入审计

- **标准要求**：《测试需求.md》§3.3.4.1（审计覆盖每个用户的重要行为）；分类依据 GB/T 25000.51-2016 可核查性
- **缺陷描述**：部分删除操作（如操作员删除业务数据）不产生审计记录
- **代码位置**：`AuditController.php` → `index()`（头部注释 DEF016, DEF017）；`ProjectController.php` → `delete()`（注释 DEF016 操作员删除不纳入审计）
- **检测方法**：用不同角色执行删除操作后查询 `audit_logs`，对比审计覆盖
- **预期结果**：✓ 缺陷存在

#### DEF017：审计覆盖不完整

- **标准要求**：《测试需求.md》§3.3.4.1（无用户、无操作遗漏）；分类依据 GB/T 25000.51-2016 可核查性
- **缺陷描述**：审计范围存在缺口，部分用户/操作未被审计记录
- **代码位置**：`AuditController.php` → `index()`（头部注释 DEF016-019）；`sql/业务库建库脚本.sql` audit_logs 表（注释 DEF016-026）
- **检测方法**：遍历执行各类操作后核查审计日志完整性
- **预期结果**：✓ 缺陷存在

#### DEF018：审计日志不记录客户端 IP

- **标准要求**：《测试需求.md》§3.3.4.2（审计记录须含操作 IP 地址）、§3.1.1（记录登录 IP）；分类依据 GB/T 25000.51-2016 可核查性
- **缺陷描述**：`client_ip` 字段恒为空字符串，不记录操作来源 IP
- **代码位置**：`index.php` → `auditLog()`（`'client_ip' => ''`）；`AuditController.php` → `index()`（注释 DEF018）
- **检测方法**：`SELECT operation_time, username, client_ip FROM audit_logs LIMIT 5;`
- **预期结果**：✓ 缺陷存在（client_ip 为空）

#### DEF019：审计时间仅精确到日期

- **标准要求**：《测试需求.md》§3.3.4.2（审计记录含事件的日期和时间）；分类依据 GB/T 25000.51-2016 可核查性
- **缺陷描述**：`audit_logs.operation_time` 为 DATE 类型，写入 `date('Y-m-d')`，同一日多条操作无法区分先后
- **代码位置**：`sql/业务库建库脚本.sql` → `operation_time DATE`（注释 DEF019）；`AuditController.php` → `index()`（注释 DEF019）
- **检测方法**：`DESCRIBE audit_logs;` 查看 operation_time 类型
- **预期结果**：✓ 缺陷存在（DATE 精度）

#### DEF020：超级管理员可删除审计日志

- **标准要求**：《测试需求.md》§3.3.4.3（审计记录受保护，防未预期删除）、§3.1.5（删除审计日志属审计范围）；分类依据 GB/T 25000.51-2016 可核查性
- **缺陷描述**：提供删除、批量删除、清空全部审计日志功能，日志无防删除保护
- **代码位置**：`AuditController.php` → `deleteall()`/`delete()`/`batchdelete()`（注释 DEF020）
- **检测方法**：以 super_admin 登录审计页执行删除，验证日志记录消失
- **预期结果**：✓ 缺陷存在

#### DEF021：审计日志备份开关无效

- **标准要求**：《测试需求.md》§3.3.4.3（审计记录定期备份）、§3.1.5（提供审计日志备份开关）；分类依据 GB/T 25000.51-2016 可核查性
- **缺陷描述**：审计备份开关可开启，但实际不会执行任何备份
- **代码位置**：`AuditController.php` → `toggleauditbackup()`（注释：状态可开启，但实际不会执行备份）
- **检测方法**：开启审计备份后检查备份目录/日志，确认无备份产生
- **预期结果**：✓ 缺陷存在

#### DEF022：审计日志容量上限过低且超限静默不记录

- **标准要求**：《测试需求.md》§3.3.4.5（审计记录满足规定的容量要求）、§3.1.5（容量达 30000 条后不再新增记录）；分类依据 GB/T 25000.51-2016 可核查性
- **缺陷描述**：`max_audit_logs = 5000`，达到上限后新日志**直接不写入**（静默丢弃），无迭代覆盖
- **代码位置**：`index.php` → `auditLog()`（注释 DEF022 容量不足，超过上限不记录）；`sql/业务库建库脚本.sql` → system_config 种子 `max_audit_logs=5000`
- **检测方法**：`SELECT config_value FROM system_config WHERE config_key='max_audit_logs';`，或生成 5000+ 条日志观察写入停止
- **预期结果**：✓ 缺陷存在

#### DEF023：审计开关可被关闭且无保护

- **标准要求**：《测试需求.md》§3.3.4.4（审计进程与设置受保护，防未授权中断变更）；分类依据 GB/T 25000.51-2016 可核查性
- **缺陷描述**：审计开关仅存于会话与 `audit_config` 表，非最高权限角色（auditor）也可关闭，关闭后全局不再记录任何审计
- **代码位置**：`AuditController.php` → `toggleaudit()`（注释 DEF023）；`index.php` → `auditLog()` 审计开关读取处（注释 DEF023）
- **检测方法**：以 auditor 登录关闭审计开关，执行操作后确认无审计日志生成
- **预期结果**：✓ 缺陷存在

#### DEF024：登录日志表从不写入

- **标准要求**：《测试需求.md》§3.3.4.1（登录行为应留痕）、§3.1.1（记录最近登录时间和登录 IP）；分类依据 GB/T 25000.51-2016 可核查性
- **缺陷描述**：`login_logs` 表结构存在但登录流程只更新 `last_login`，从不向登录日志表写入记录，登录行为无完整审计
- **代码位置**：`LoginController.php` → `authenticate()`（更新 last_login、无 login_logs 写入，注释 DEF024）
- **检测方法**：多次登录登出后 `SELECT COUNT(*) FROM login_logs;` 恒为 0
- **预期结果**：✓ 缺陷存在

#### DEF025：备份文件明文存储无加密

- **标准要求**：《测试需求.md》§3.3.1.5（数据加密存储）、§3.3.2.2（备份文件完整可复用）；分类依据 GB/T 25000.51-2016 可核查性
- **缺陷描述**：备份生成的 SQL 文件明文存放于 `backups/` 目录，无加密、无访问控制，含全部业务数据与用户信息
- **代码位置**：`BackupController.php` → `create()`（直接写 SQL 文件到 `BACKUP_PATH`）
- **检测方法**：打开 `backups/` 目录下的备份文件查看明文数据
- **预期结果**：✓ 缺陷存在

#### DEF026：会话无超时控制

- **标准要求**：《测试需求.md》§3.3.5.2（登录连接超时自动退出）；分类依据 GB/T 25000.51-2016 可核查性

- **代码位置**：`index.php`（无 session 超时检查逻辑）

- **预期结果**：✓ 缺陷存在

#### DEF027：支持创建重复账号

- **标准要求**：《测试需求.md》§3.3.5.1（身份标识具有唯一性）；分类依据 GB/T 25000.51-2016 真实性

- **预期结果**：✓ 缺陷存在

#### DEF028：登录失败无次数限制

- **标准要求**：《测试需求.md》§3.3.5.2（限制非法登录次数、失败锁定）；分类依据 GB/T 25000.51-2016 真实性

- **预期结果**：✓ 缺陷存在

## 四、缺陷验收标准

1. **缺陷存在性**：缺陷能在系统中明确观察到（未被隐藏或修复）

3. **检测可行性**：使用常规安全测试方法可检出
4. **功能无影响**：缺陷不影响系统基本功能正常运行
5. **等级适当**：均为中低风险，无远程代码执行等高危漏洞
